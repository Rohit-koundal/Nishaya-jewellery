# Bulk catalog workspace

## Owner workflow

1. Open **Admin → Product Drafts → Create from photos**. Choose up to 30 JPG/PNG/WebP images (2MB each), or a supplier folder.
2. Check the proposed groups. Explicit references such as `E100_front.jpg` / `E100_side.jpg` and product subfolders suggest groups. Camera counters and visual similarity do not. Move photos, merge groups, split an image into a separate product, and select a cover as needed. Each group supports up to 12 photos. Clicking **Confirm groups & create** approves the grouping.
3. **Run Smart Fill automatically after upload** is enabled by default and explicitly uses the existing Gemini quota. It analyses up to three views per product, with the cover first. No new AI or image-storage provider is introduced.
4. In the batch workspace, use shared verified supplier notes, common category, prices, stock and specifications as appropriate. Defaults only fill empty fields, and preserve a stock value of zero. New photo drafts leave stock unknown. Product-specific notes and supplier references remain separately editable. Reusable defaults are opt-in and saved on the current browser for the store; load/review/apply them explicitly.
5. Review the photos, source evidence, required-field checklist and inline listing details. Filter by ready/review/failed/processing/published. Language and tone can be set in shared defaults; single-product Smart Fill exposes the same preferences. The existing project had no dedicated store-wide content-language/tone setting, so there is no hidden global preference being overwritten.
6. **Save inline changes** saves corrections together. Publication also saves the relevant corrections first. **Full details** opens the existing draft editor for shipping, variants, policies, media and other advanced fields. Known facts can be confirmed manually with **I have reviewed these details**, without paying for another AI call.
7. Click **Publish selected ready products**. Missing required information remains in drafts, and individual publishing failures are displayed. Optional copy, SEO, shipping hints or certificates do not alone block publication. Zero stock is explicit and publishable, but unavailable for purchase.

## Reliability and safeguards

- Single-product and draft analysis share the same backend analysis function, prompt, source checks and effective category specifications. Photo-based appearance is distinguished from supplier/source statements.
- No visual guesses for prices, MRP, stock, weight, dimensions, metal, purity, gemstone authenticity or warranty. Verified common defaults and explicit supplier information can supply these; unknown required facts stay pending.
- Existing values are protected by default. Regenerate only a chosen copy field or explicitly choose all listing copy. Inventory/variants are never regenerated by Smart Fill.
- Draft revisions protect concurrent edits. Processing has a per-draft server lease and a fingerprint of inputs/configuration. Unchanged successful analysis can be reused. Changed source photos/notes require review.
- Requests run sequentially, at least six seconds apart. Quota/account/network errors pause further work; retries are explicit. A failed product does not undo completed saves.
- Each result/status is saved to MongoDB, not only browser memory. Closing the page stops scheduling new requests; an in-flight server request can finish. Refresh, select the affected drafts and reopen **Smart fill / review selected products** to continue. A server process interrupted mid-request has a 90-second lease timeout before safe retry. This is a resumable foreground workflow, not an unattended background worker.
- Unsaved inline corrections have browser recovery. Stale corrections are shown separately rather than replacing a newer server revision. Browser-private mode/storage limits can disable this extra recovery; completed server saves remain intact.
- Existing category IDs are used; Smart Fill creates no categories. Existing permissions/licence checks, SKU/variant/stock validation, and the `sourceDraftId` duplicate-publication guard remain in use.
- Uploaded images are reused. The existing compression settings and stored-image quality are unchanged. Unique staging filenames prevent identically named supplier photos overwriting one another.

## Deployment / verification

Deploy **both** the frontend and nested `backend` repository. No new secret/env variable is introduced. Photo AI needs the existing `GEMINI_API_KEY`, usable quota and the deployment's `aiProduct` entitlement. MongoDB and existing image storage must already work.

The additive ProductDraft schema adds supplier notes, brand and processing metadata. Existing drafts remain readable; no destructive migration is required.

Tests cover photo grouping, field completeness, paragraph/highlight preservation, inherited required specifications, partial failures, leases/replay, manual edits, refresh recovery, permissions and duplicate-safe publication. AI/provider responses are mocked in automated tests: a controlled staging run with real product photos is still needed to assess actual description quality and provider quota/latency.

Recommended smoke test: two products with two views each → confirm grouping → analyse → enter verified prices/stock/material/weight → save/reload → publish one → retry its publish → verify only one product exists, with all copy/specifications/images intact.
